## 1. `npm run ci` was red, and the reason was two copies of one claim

`smoke:capability` failed on its first check, `reconcile_in_sync: false`. The
cause was not the capability inventory being wrong — it was the inventory and
the overlay disagreeing about MONA-CAP-052:

- R07 added the typed approval reply path and updated the **row** in
  `docs/codewhale-capabilities-macos.json` (`tests`, `gap`, entry label). That
  row now says the reply routes are wired and verified and that only a live
  approval decision is unproven.
- `tools/p18-coverage/reconcile.mjs` still carried the P08 text, so every
  `--write` regenerated the **coverage block** from the stale sentence:
  *"Answering an approval has no IPC path yet."*

The generated summary and the row described different products. R07's statement
is the true one — `scripts/pending-smoke.mjs` proves both routes against the
pinned engine — so the overlay was corrected to carry it, then the inventory was
regenerated by the tool (`node tools/p18-coverage/reconcile.mjs --write`) rather
than hand-edited. `--check` and `smoke:capability` are green again (17/17).

This is the failure mode the gate exists for: a claim stored twice must be
reconciled by the generator, not by whoever notices.

## 2. Twenty React act warnings, on a green suite

The review queue left 20 `An update to … was not wrapped in act(...)` warnings
across four tests in `test/settings-screen.test.tsx` — green tests, and a warning
that said the test's own assertions were not observing the state it claimed to.

R12's prompt is explicit that these are fixed at the `act`/await boundary, not
silenced. Two defects were behind them:

- **The boundary was synchronous.** `Settings` mounts every tab, and
  `FinderIntegration` and `UpdateSettings` read the bridge from an effect. Their
  promises settle one microtask after a synchronous `act()` returns, so their
  state updates landed outside act. The harness now renders and settles inside an
  async act (`settle()` awaits the pending microtasks inside `act`); the tests
  await it. Warnings: 20 → 0.
- **The stub was lying about a contract.** With the updates inside act, the
  render crashed: `FinderIntegration` reads `status.recovery.length`, and the
  generic test proxy answered *every* bridge method with an `IpcResult` refusal —
  including `serviceStatus()`, whose contract in `src/shared/contracts/bridge.ts`
  is `Promise<ServiceStatus>`, never a result envelope. The harness now answers
  each API with its documented "nothing here" shape: a real not-installed
  `ServiceStatus` for `serviceStatus`/`refreshService`, the refusal envelope for
  the rest. The product code did not change; the fixture stopped asserting a
  contract the product never promised.

`artifacts/r12-act-warnings-before.txt` is the captured stderr from HEAD's
harness on this host; `artifacts/r12-ci.txt` is the same file after the fix, with
0 warnings.

## 3. The lint gate could not see the R11 blocker

RD-023 records it plainly: R11's blocker (`Rendered more hooks than during the
previous render`, reachable from the empty state's own Open folder button) threw
at runtime while `npm run lint` reported zero errors, because no `react-hooks`
plugin was configured. "Lint 0 errors" was never evidence for that class.

- **`eslint-plugin-react-hooks` 7.1.1** is pinned as a devDependency (exact
  version, `npm audit` 0 vulnerabilities), and
  `react-hooks/rules-of-hooks: "error"` applies to `src/renderer/**`.
- **`exhaustive-deps` is deliberately not enabled.** It reports on almost every
  effect in this codebase; switching it on would change the lint result for files
  this queue did not touch. That is its own task with its own evidence.
- **It found one real defect immediately.** `useFavorite` in `Shell.tsx` was a
  plain `useCallback` callback named like a hook. It works, but the name makes the
  rule (and Fast Refresh) treat it as a hook, so a future refactor that called it
  conditionally would be invisible. Renamed `insertFavorite` — behaviour
  unchanged, palette and prop wiring included.

The gate is a mechanism, not a claim: `test/lint-hooks-gate.test.ts` lints source
text through the repository's own `eslint.config.mjs` and asserts that a hook
after an early return and a `use`-named callback called from a plain function are
both rejected, and that top-of-component hooks and custom hooks are accepted.
`artifacts/r12-hooks-gate-off.txt` is that test run with the rule set to `off`:
2 of 3 fail. With the rule on, all 3 pass.
